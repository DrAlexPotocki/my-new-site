Техническое задание и постоянные правила проекта

1. Общая информация о проекте

Разрабатывается новый сайт для врача мануального терапевта Алєксандра Потоцького.

Сайт создаётся с нуля на HTML, CSS и JavaScript с использованием Vite.

Основной адрес сайта: https://am.if.ua/

Старый сайт на WordPress продолжает работать отдельно. Новый проект разрабатывается независимо. Изменения в новом проекте не должны затрагивать старый сайт.

Основная задача

Создать современный, понятный и профессиональный сайт врача, который:

знакомит посетителей с врачом и его подходом к работе;

объясняет возможности и ограничения мануальной терапии;

помогает пациентам разобраться в проблемах опорно-двигательного аппарата;

предоставляет полезную медицинскую информацию;

позволяет ознакомиться с рекомендациями и упражнениями;

помогает записаться на приём.

Сайт должен формировать доверие за счёт понятной информации, профессионального содержания и единого визуального стиля.

2. Технологии и ограничения

Используемый стек:

HTML;

CSS;

JavaScript;

Vite.

Не использовать:

React;

Vue;

Angular;

WordPress;

другие фреймворки и CMS без отдельного согласования.

Проект должен оставаться относительно простым для поддержки и дальнейшего развития.

Весь код должен быть понятным, структурированным и не содержать неоправданно сложных решений.

Принципы разработки

Не переписывать работающие части сайта без необходимости.

Не менять архитектуру проекта ради небольших задач.

Не устанавливать дополнительные библиотеки, если задача решается средствами текущего стека.

Не дублировать код, если уже существует подходящий общий компонент или скрипт.

Использовать существующие компоненты, стили и данные.

Не вносить несогласованные изменения в другие страницы.

Сохранять работоспособность уже созданных страниц после каждого изменения.

3. Структура проекта

Основная структура:

index.html — главная страница;

src/main.js — JavaScript главной страницы;

src/style.css — общие стили сайта;

src/components/ — общие HTML-компоненты;

src/scripts/ — общие JavaScript-функции;

src/data/ — общие данные сайта;

src/pages/ — JavaScript отдельных страниц;

public/ — изображения, логотипы, иконки и другие статические файлы.

HTML-файлы внутренних страниц располагаются в корне проекта, если для конкретной страницы уже используется такая архитектура.

Основные принципы организации

Общие элементы сайта должны использоваться повторно.

Данные, которые используются на нескольких страницах, по возможности хранятся централизованно.

Логика отдельных страниц должна находиться в соответствующих JS-файлах.

Стили отдельных страниц добавляются в общий CSS, если нет необходимости создавать отдельную систему стилей.

Не создавать дополнительные файлы и папки без практической необходимости.

Общие требования к дизайну

Минималистичный и спокойный медицинский стиль.

Достаточное количество свободного пространства.

Хорошая читаемость текста.

Чёткая визуальная иерархия.

Аккуратные карточки и блоки.

Единые отступы, радиусы и оформление элементов.

Отсутствие чрезмерного количества декоративных элементов.

Адаптация под мобильные устройства, планшеты и компьютеры.

Не использовать чрезмерные анимации, сложные эффекты и визуальные решения, которые мешают восприятию информации.

Важное правило

Новые страницы не должны выглядеть как отдельные проекты. Они должны восприниматься как естественное продолжение одного сайта.

При создании новой страницы сначала изучать оформление уже существующих аналогичных страниц и использовать их структуру и CSS-классы.

Не создавать новый визуальный стиль без необходимости.

Принцип организации страниц

Например:

страница «Мануальна терапія» объясняет метод, его возможности и ограничения;

раздел «З чим я працюю» знакомит с основными проблемами, с которыми обращаются пациенты;

раздел «Пацієнтам» отвечает на организационные вопросы;

7. Правила создания новых страниц

Перед созданием новой страницы необходимо:

Определить её назначение.

Проверить, нет ли уже страницы с аналогичной задачей.

Найти существующую страницу, которая подходит в качестве образца.

Изучить её HTML, JS и используемые CSS-классы.

Сохранить общую структуру и визуальный стиль сайта.

Технические требования

Использовать существующие Header и Footer.

Подключать общий файл стилей.

Использовать существующий скрипт меню.

Подключать необходимые общие функции.

Добавлять favicon.

Проверять работу страницы на мобильных устройствах.

Проверять ссылки, кнопки и загрузку изображений.

Не менять глобальные стили, если задача решается небольшим локальным дополнением.

Если дополнительный CSS не нужен, прямо указывать: «Дополнительный CSS не требуется».

8. Правила разработки медицинской библиотеки

Медицинская библиотека — один из основных информационных разделов сайта.

Её задача — последовательно и понятно объяснять пациентам проблемы позвоночника, причины симптомов, методы диагностики и подходы к лечению.

Библиотека должна развиваться как единая система взаимосвязанных материалов, а не как случайный набор статей.

Основные направления

Межпозвоночные диски и связанные с ними изменения.

Дегенеративные изменения позвоночника.

Изменения замыкательных пластинок позвонков.

Фасеточные суставы.

Стеноз и компрессия нервных структур.

Радикулопатии и другие нарушения со стороны нервных корешков.

Структурные изменения позвоночника.

Боль в шейном, грудном и поясничном отделах.

Боль между лопатками.

Боль с распространением в руку или ногу.

Перед добавлением новой статьи

Обязательно:

Проверить существующий каталог статей.

Определить, раскрыта ли уже эта тема.

Проверить, не дублирует ли новая статья существующий материал.

Определить, какую новую информацию она даст читателю.

Найти связанные статьи для внутренней перелинковки.

Определить, какие существующие статьи при необходимости должны ссылаться на новую.

Не предлагать новые статьи только ради увеличения количества материалов.

Не создавать несколько статей, которые отличаются преимущественно названием, но раскрывают одну и ту же проблему.

Формат предложения новой статьи

При предложении новой темы указывать:

название на украинском языке;

краткое содержание;

чем тема отличается от уже существующих статей;

с какими существующими статьями её можно связать;

какую практическую пользу получит пациент.

Не заявлять о высоком поисковом спросе без проведения отдельного SEO-анализа.

9. Медицинская точность и авторский стиль

Все медицинские материалы должны быть профессиональными, понятными и корректными.

Авторский стиль — врач Алєксандр Потоцький.

Требования к текстам

Основной язык сайта — украинский.

Стиль — спокойный, профессиональный и понятный.

Не использовать рекламные преувеличения.

Не запугивать пациента.

Не давать необоснованных обещаний результата.

Не использовать искусственные повторения и шаблонные фразы.

Не писать от имени команды, если материал представлен от лица врача.

Объяснять медицинские термины простым языком, не искажая их смысл.

Требования к медицинской достоверности

Различать изменения на МРТ и реальные симптомы пациента.

Не утверждать, что любое обнаруженное изменение на снимке обязательно вызывает боль.

Не утверждать, что мануальная терапия вправляет диски, устраняет грыжи или физически возвращает позвонки на место.

Не представлять переход протрузии в экструзию и секвестрацию как обязательную последовательность.

Учитывать индивидуальные особенности пациента.

Указывать ограничения метода и ситуации, когда мануальная терапия не подходит.

При наличии показаний объяснять необходимость консультации невролога, ортопеда, нейрохирурга или другого специалиста.

Отдельно обозначать симптомы, при которых требуется срочная медицинская помощь.

Медицинские утверждения должны опираться на достоверные источники. При необходимости добавлять в статью блок с источниками и рекомендациями.

Не выдумывать исследования, статистику, медицинские рекомендации и ссылки.

11. Внутренняя перелинковка статей

Медицинская библиотека должна иметь логичную сеть внутренних ссылок.

Цель — помочь читателю перейти от общего материала к более подробным объяснениям связанных проблем.

Используем два вида ссылок

1. Контекстные ссылки внутри текста

Добавляются там, где упоминается тема, подробно раскрытая в другой статье.

Анкор должен естественно вписываться в предложение и понятно описывать содержание целевой статьи.

2. Блок «Читайте також»

Размещается после основного содержания статьи.

В блоке рекомендуется показывать 2–3 действительно связанные статьи.

Не добавлять случайные ссылки только ради количества.

Централизованная система

Связи между статьями хранятся в src/data/articlesData.js.

Для каждой статьи используется поле:

relatedArticles

В нём указываются ID связанных статей из общего каталога.

Пример:

relatedArticles: [2, 3, 14]

ID должны соответствовать реально существующим статьям.

Правила перелинковки

Не ссылаться на несуществующие страницы.

Не добавлять ссылку на саму статью.

Не повторять один и тот же набор рекомендаций без смысловой причины.

Использовать понятные названия и естественные анкоры.

Проверять ссылки после добавления новой статьи.

При появлении новой статьи проверять, нужно ли добавить на неё ссылки из уже существующих материалов.

Блок рекомендаций должен быть единообразным на всех страницах библиотеки.

Не переписывать существующие статьи целиком ради добавления ссылок. Вносить только необходимые точечные изменения.

12. SEO и доступность

SEO должно развиваться вместе со структурой и качеством сайта.

Основные требования:

уникальный и понятный title для каждой страницы;

корректный meta description;

один основной H1;

логичная иерархия H2 и H3;

осмысленные URL;

понятные внутренние ссылки;

корректные alt у содержательных изображений;

отсутствие дублирующегося текста;

корректная работа сайта на мобильных устройствах.

Не использовать чрезмерное количество ключевых слов.

Не создавать тексты исключительно ради поисковых систем. Приоритет — полезность и понятность для пациента.

SEO-изменения не должны ухудшать медицинскую точность и естественность текста.

16. Правила взаимодействия при разработке

Пользователь не является профессиональным программистом, поэтому инструкции должны быть простыми и последовательными.

При предоставлении изменений:

Указывать точный путь к файлу.

Объяснять, что именно нужно найти.

Указывать, что удалить, заменить или куда вставить код.

Если файл нужно создать — указывать точное имя и расположение.

Не давать несколько альтернативных способов, если один способ достаточен.

Не перегружать объяснениями и не предлагать ненужные изменения.

При необходимости предоставлять полный готовый код файла.

Если изменения затрагивают HTML и JS, предоставлять оба файла вместе.

Не предполагать, что пользователь уже применил предложенный код, пока он это не подтвердил.

Работать небольшими последовательными этапами.

После каждого важного изменения пользователь проверяет результат, и только после подтверждения переходим к следующему шагу.

18. Главный принцип развития проекта

Сайт должен развиваться последовательно, без хаотичных изменений.

Приоритеты:

Надёжная и понятная архитектура.

Единый визуальный стиль.

Корректная работа всех страниц.

Медицинская достоверность.

Полезность материалов для пациентов.

Логичная структура медицинской библиотеки.

Внутренняя перелинковка.

Постепенное развитие SEO.

Любое новое решение должно улучшать сайт как единую систему, а не создавать отдельный, несвязанный элемент.
